# Требования к менеджеру задач студенческой группы

Проект по варианту № 8 — лёгкое консольное приложение для ведения дел студенческой группы.
Документ фиксирует требования из задания и согласованный план постепенной разработки на три недели.
Точные даты сдачи и границы спринтов преподавателем в предоставленных материалах не указаны.

## Пользователи и назначение

Староста и студенты используют приложение, чтобы вести общий список домашних заданий,
дедлайнов и дел группы без отдельной регистрации. Управление выполняется через терминал.

## Требования из описания варианта

| ID | Требование | Критерий приёмки итоговой версии |
| --- | --- | --- |
| FR-01 | Общий список дел группы | Пользователь добавляет задачу и видит её в списке с уникальным ID. |
| FR-02 | Приоритеты задач | При создании задачи можно выбрать низкий, средний или высокий приоритет; он отображается в списке. |
| FR-03 | Отметка выполнения | Пользователь отмечает задачу выполненной по ID и видит её новый статус. |
| FR-04 | Консольное управление | Все основные действия доступны в терминале, регистрация не требуется. |

Три уровня приоритета и обращение по ID — принятые решения реализации;
само описание требует назначения приоритетов и отметки выполненных задач, не задавая их формат.

## Принятые требования проекта

| ID | Решение | Критерий приёмки итоговой версии |
| --- | --- | --- |
| PR-01 | Сохранение в JSON-файл | После выхода и повторного запуска задачи, их ID, приоритеты и статусы восстанавливаются. |
| PR-02 | Один общий файл данных | Приложение работает с одним списком группы. Сетевой доступ и одновременное редактирование с разных компьютеров в первую версию не входят. |
| PR-03 | Проверка ввода | Пустое название и неверная команда не приводят к аварийному завершению. Ошибочный ID при будущих операциях вызывает понятное сообщение. |
| PR-04 | Python | Код написан на Python 3.10 или новее; текущая версия использует только стандартную библиотеку. |

Сохранение в JSON принято командой для практического использования списка.
Описание варианта не задаёт формат хранения данных.

## Требования к сдаче по материалам практики

- Рабочая версия соответствует заданию и готова к демонстрации в срок спринта.
- В репозитории есть README с воспроизводимой инструкцией запуска.
- Приложение запускается в Docker. Файл данных сохраняется вне удаляемого контейнера.
- Git-история отражает реальные этапы разработки; передача одного архива не заменяет историю.

Проверка сохранности данных после пересоздания контейнера — критерий команды
для выполнения PR-01 при запуске через Docker.

## Первый этап

В текущий этап входят:

1. Меню с просмотром задач, добавлением и выходом.
2. Создание задачи с целочисленным ID и названием.
3. Последовательные ID, начиная с 1 в новом сеансе.
4. Просмотр пустого списка и списка добавленных задач.
5. Отклонение пустого названия и названия из пробелов.
6. Удаление пробелов по краям названия.
7. Понятное сообщение при неизвестной команде с возвратом к меню.

На этом этапе данные хранятся только в памяти до завершения программы.
Приоритеты, выполнение, JSON и Docker ещё не реализованы;
первый этап не является готовой итоговой версией проекта.

Этап готов к фиксации в Git после проверки перечисленных сценариев.
Результаты проверки записываются в `docs/checklist.md`.

## План следующих этапов

- Неделя 1: требования, структура, меню, добавление и просмотр задач.
- Неделя 2: приоритеты, отметка выполнения, сохранение и загрузка JSON.
- Неделя 3: итоговые тесты, Docker, проверка сохранности данных, README и демонстрация.

План корректируется, если преподаватель выдаст отдельные задания по спринтам.
Срок задачи, ответственный, редактирование, удаление и фильтры — возможные расширения;
в обязательный объём первой версии они пока не включены.

## Распределение работы

- Lead Developer: архитектура, основной код, объединение модулей, исправление ошибок.
- Product Owner: требования, задачи и сроки, актуальность README, сценарий демонстрации.
- QA/DevOps: проверки и отчёты об ошибках, автоматические тесты, Docker и организация работы с Git.

Каждый участник фиксирует свои реальные изменения от своего имени.
